# Архитектура — AllMusic Player

**Редакция 0.1 утверждена владельцем; уточнения задачи 000 от 29.10.2026. Полная архитектура пока не реализована.**

## 1. Главная идея

Одна кодовая база Qt 6/C++/CMake с общим прикладным ядром и двумя QML-оболочками. Компоненты не знают особенностей конкретного UI. Сетевой сервер хранит аудио; на каждом устройстве — отдельные локальная БД и кэши. Никакого обязательного собственного API-сервера. Первая версия только читает облако.

```text
                 ┌────────────────────────┐
                 │ UI: Desktop QML        │
                 │ UI: Android QML        │
                 └────────────┬───────────┘
                              │ presentation/view-models
                 ┌────────────▼───────────┐
                 │ Application services   │
                 │ library, queue, sync   │
                 └───┬────────┬────────┬──┘
                     │        │        │
             ┌───────▼──┐ ┌───▼────┐ ┌▼─────────────┐
             │ WebDAV   │ │ Audio  │ │ Metadata /   │
             │ client   │ │ engine │ │ artwork      │
             └───────┬──┘ └───┬────┘ └──────┬───────┘
                     │        │             │
             ┌───────▼────────▼─────────────▼───────┐
             │ SQLite + durable audio/artwork caches │
             └───────────────────────────────────────┘
                            │
                ┌───────────▼───────────┐
                │ Android OS bridge     │
                │ (только Android)      │
                └───────────────────────┘
```

Диаграмма логическая: воспроизведение не должно зависеть от SQLite в горячем цикле декодирования/вывода звука.

## 2. Модули и границы ответственности

| Модуль | Отвечает за | Не должен делать |
|---|---|---|
| `cloud/` | WebDAV, безопасные пути, HTTP, ответы, ошибки, повторные запросы | Читать QML или напрямую менять БД |
| `sync/` | План и очередь сканирования, сравнение ревизий, задания на метаданные | Блокировать UI |
| `metadata/` | Чтение тегов, длительности и встроенных картинок, приоритеты источников | Записывать оригинальные файлы в v1 |
| `library/` | Модели исполнителей/альбомов/композиций, SQLite-репозитории, поиск | Скачать все обложки при открытии списка |
| `artwork/` | Извлечение, ограничение размеров, дедупликация, инвалидация миниатюр | Хранить оригинальные многомегабайтные картинки без необходимости |
| `cache/` | Загрузка аудиофайлов, целостность, квоты, pinned/offline, eviction | Самостоятельно выбирать UI-экраны |
| `playback/` | Декодирование/звук, очередь, seek, prefetch, переходы | Осуществлять WebDAV-запись |
| `platform/` | Keychain/credential manager, аудиофокус/системные медиа-кнопки, фоновые службы | Встраивать бизнес-логику в Android bridge |
| `ui/desktop/` | Компьютерные экраны QML | Прямые WebDAV-запросы |
| `ui/android/` | Мобильные экраны QML | Свою отдельную медиатеку и кэш |
| `tests/` | Unit, интеграционные, имитационный сервер, эталонные аудиофайлы | Подключение к личному облаку в CI |

## 3. Контракты (договорённости между компонентами)

Контракты — предварительные имена, их ещё можно уточнить без потери концепции:

- `ICloudProvider`: `listDirectory`, `stat`, `openRange`/`download`, `capabilities`, `cancel`; провайдер отдаёт нормализованные `RemoteEntry` и классы ошибок. В первой версии единственная реализация `MailWebDavProvider`.
- `ILibraryRepository`: транзакционное чтение/запись индекса SQLite, поиск, обновление отдельных записей.
- `IMetadataExtractor`: теги/обложки/длительность из локальных файлов или предоставляемого потока с random-access; конкретный метод зависит от экспериментальной проверки.
- `IPlaybackEngine`: `play/pause/seek/stop`, события времени, состояния, ошибок и готовности буфера; реализация скрыта за интерфейсом.
- `ICacheStore`: `get`, `startDownload`, `commitVerified`, `pin`, `evict`, `invalidate`, `statistics`.
- `IArtworkProvider`: источник изображений, преобразование, выдача миниатюр и сигнал инвалидации.
- `ISecureCredentialStore`: получение/сохранение учётных данных через платформенное API с безопасным пользовательским вводом.

Не реализовывать большой динамический plugin-loader до появления реальной потребности; интерфейсы/DI достаточно для будущего расширения.

## 4. Данные: модель и индексация

Предварительные таблицы SQLite (без преждевременного проектирования всех колонок):

- `sources`: тип, URL, путь базы `/AllMusic`, состояние синхронизации (без паролей).
- `remote_entries`: источник, нормализованный путь, тип, размер, дата изменения, ETag, время последней проверки, состояние удаления/неизвестной версии.
- `tracks`: ссылка на remote entry, поля тегов, длительность, кодек, признаки ошибок чтения.
- `albums`, `artists`, `album_tracks`: группировка по тегам; особая обработка Album Artist, сборников, multi-disc.
- `artworks`: hash изображения, путь к преобразованному файлу, размеры, способ получения, дата ревизии.
- `track_artwork` / `album_artwork`: связь записей и изображения.
- `cache_entries`: идентификатор трека/ревизии, путь на диске, состояние, объём, контрольная информация, LRU, pinned/offline.
- `playlists`, `playlist_tracks`, `favorites`, `settings`: локальные пользовательские данные.
- `sync_jobs`: отдельные задания и ошибки при синхронизации (если необходимо для восстановления).

Миграции БД версионировать. Запрещено молчаливо удалять пользовательские плейлисты/избранное при переиндексации; индексные метаданные и данные пользователя логически раздельны.

## 5. WebDAV и граница `/AllMusic`

- Использовать HTTPS и штатную верификацию сертификатов. Пароль для внешнего приложения не передавать через командную строку или URL.
- `PROPFIND Depth: 1` для перечисления папки; корректно разбирать `207 Multi-Status`, XML namespace, пути с пробелами, кириллицей, `%`, `#` и необычными символами.
- Все `href` приводить к канонической форме; отклонять внешние хосты и выход за корень после декодирования/нормализации, включая `..`, неоднозначные разделители и редиректы.
- Перед аудиоплеером не полагаться на наличие `Accept-Ranges`; реально запросить `Range` и проверить `206`, `Content-Range`, длину, точность байтов. `200` считать ответом сервера без корректной поддержки диапазона, а не нужным фрагментом.
- Обрабатывать 401/403/404/408/429/5xx; поддерживать отмену, ограниченный backoff с jitter, очередь и ограничение конкурентных запросов.
- Операции записи в v1.0 физически отсутствуют в публичном интерфейсе провайдера; дополнительно проверяются mock-сервером/HTTP-spy.
- Проверять на имитационном сервере и тестовых данных; реальный сервер — вручную, только после явного разрешения владельца и безопасной локальной настройки пароля.

## 6. Аудио: сначала прототип, потом выбор движка

Возможные реализации:

A. `QMediaPlayer` / Qt Multimedia (с FFmpeg backend), воспроизведение из подготовленного локального файла или управляемого источника. Плюсы: меньше собственной аудиологики; минусы: недостаточный контроль seek/gapless/буферизации на некоторых платформах.

B. Управляемая подача декодированного PCM через `QAudioSink` плюс подходящий декодер/FFmpeg. Плюсы: тонкий контроль gapless и очереди; минусы: больше рисков потоков/временных меток и упаковки FFmpeg.

**Общий production `PlaybackEngine` не выбран.** Для Desktop остаются исследовательские варианты Qt Multimedia и управляемой PCM подачи; проверить форматы, seek и потоковую буферизацию до выбора. Отдельное решение Issue #26 выбирает только узкий Android Media3 spike и не меняет Desktop реализацию или общий production контракт. Никакого «точного gapless» по умолчанию до подтверждённых тестов.

Пути данных: WebDAV → контроллер загрузки → атомарный дисковый аудиокэш → источник декодирования → вывод звука. При подтверждённой поддержке Range возможны частичные сегменты; без неё нужен обоснованный fallback — скачивание целого файла до перемотки или иное UX-ограничение.

Приоритет запросов: (1) текущий трек, (2) seek текущего, (3) ближайший следующий, (4) ручной офлайн, (5) сканирование обложек/метаданных. Никаких операций с SQLite/сетью на realtime-аудиопотоке.

## 7. Кэширование

Три независимых класса: (а) SQLite + индекс, (б) миниатюры, (в) аудиоданные. Диски кэша раздельны на устройствах, облачный каталог общий. Полностью скачанный файл получает состояние `verified` только после проверки размера, завершения загрузки и, если есть, контрольной версии ресурса; незавершённые `.part` не предлагаются как офлайн. Процедуры восстановлений после аварийного завершения обязательны.

Обложки: локальный hash-контент, максимальная базовая размерность (начально 256 px, проверить UI/HiDPI), дедупликация по хешу, адаптивная загрузка; при изменении remote-entry метаданные и обложка помечаются `stale`. Неизменные ETag/size/time — оптимизация, не криптографическое доказательство неизменности. Встроенная картинка может находиться не в начале файла, поэтому не обещать сетевое извлечение за один маленький диапазон.

Настройки: общий лимит, отдельная квота офлайн, управление очисткой, показ реального дискового пространства; предварительные значения утверждаются по результатам испытаний.

## 8. Асинхронность и устойчивость

- QML и UI-thread не должны делать блокирующих вызовов сети, БД или декодирования.
- Сетевые операции и БД через очередь задач/рабочий контекст; соблюдать потоковую принадлежность Qt-объектов (особенно `QNetworkAccessManager` и SQL connections).
- Работа в фоне ограничивается сетевой политикой устройства, а на Android — жизненным циклом media session/foreground service.
- Долгие задания поддерживают отмену, ограниченный параллелизм, устойчивое возобновление, idempotency где возможно.
- Метрики: длительность сканирования, ошибки сети, hit-rate аудио/арт-кэша, недогрузки и время подготовки трека; без отправки данных на внешние сервера по умолчанию.

## 9. Платформенная интеграция Android

В границах Issue #26 Android использует тонкий Java `Media3PlaybackAdapter` в
`android/src`, управляемый QObject-контроллером из C++ через JNI и показанный в
существующем Qt Quick экране. Закреплён только `androidx.media3:media3-exoplayer`
1.11.1. ExoPlayer оставлен на стандартных Android MediaCodec renderers и
AudioTrack; собственные декодеры и Qt Multimedia/FFmpeg в Android target не
подключены. Источники — только небольшие синтетические APK assets MP3/FLAC и WAV
для регрессии; сеть и доступ к файлам пользователя не нужны.

Контроллер показывает активный трек, состояние, позицию, длительность и ошибку;
переключение заменяет текущий MediaItem. При уходе приложения с переднего плана
воспроизведение останавливается, а при завершении Java ExoPlayer освобождается.
`MediaSessionService`, фон, lock-screen controls, аудиофокус и специальные
разрешения не входят в spike. Сборка и CI не доказывают слышимый звук, поддержку
MP3/FLAC/seek или конкретные Bluetooth/USB маршруты: это остаётся ручной проверкой
владельца на Huawei.

Issue #24 подключает к этой границе `ProgressiveMediaSource` с собственной
Media3 `DataSource`. JNI получает только непрозрачный числовой handle, смещение,
длину и байты. URI MediaItem содержит только этот handle; Cloud Mail URL,
внутренний путь и HTTP заголовки остаются в C++. Java получает только handle;
QML получает только отображаемые подписи элементов, не внутренние пути или URL.
Реквизиты остаются в C++ и не передаются Java/QML. Android
CMake подключает `mail-webdav-diagnostic` и отдельную библиотеку Range без
`Qt6::Multimedia`; Desktop target `local-playback` сохраняет прежний playback
путь.

Каждый handle удерживает Range-устройство до завершения текущего JNI read.
Чтения сериализованы одним mutex на источник и идут только с Media3 loader;
`MailWebDavRangeDevice` отправляет сетевые операции своему Qt worker потоку.
Media3 close/stop отправляет атомарное прерывание текущего GET, а Disconnect,
смена источника и выход помечают handle отозванным, отменяют worker-запрос и
удаляют устройство после завершения чтения и остановки worker. Qt UI не ждёт
чтения байтов. `DataSpec.position`, известная длина и `LENGTH_UNSET` передаются
через seek/size; Java мост ограничивает один read 64 КиБ. Range-ядро сохраняет
лимит каждого GET, кэш 4 × 64 КиБ, HTTP 206/Content-Range/framing/ETag-проверки,
строгий TLS, запрет редиректов и отсутствие fallback на HTTP 200.

Для Android APK требуется только `android.permission.INTERNET`; доступ к
состоянию сети, медиа, файлам, Bluetooth или фоновому сервису не добавляется.
Изменение реализуется в Issue #24 и требует mock/CI проверки, включая отложенный
Range GET во время Stop/Disconnect и повторное открытие после seek.

## 10. Сборка, CI, лицензии

- CMake; воспроизводимые версии зависимостей и фиксированная минорная ветка Qt (точную версию выбрать в этапе 0, не гнаться за последней ради обновления).
- GitHub Actions отдельно для Windows, Linux и Android; CI для статической проверки/тестов и сборок, не является доказательством качества звука на устройствах.
- Отчёт о лицензиях и бинарных зависимостях: Qt LGPL/GPL/коммерческая модель, FFmpeg, TagLib; требования по сборке, распространению, ссылкам на исходники и bundled libraries — отдельная проверка до публикации пакетов.
- Secrets только в хранилищах окружений/локально у пользователя, не в Git, не в тестовых фикстурах и не в диагностических отчётах.

## 13. Основание сборки и реальные платформы — 29.10.2026

Задача 000 реализует только `src/app/` и `ui/desktop/`: один экран Qt Quick.
Используется открытая Qt 6.12.0, C++17, CMake 3.30.5 и Ninja 1.12.1.
Обязательная среда Linux CI — Ubuntu 24.04 x64 / GCC 13.x; Windows CI —
windows-2022 / MSVC 2022 toolset 14.44 / x64. Образ Windows Server не является
ни Windows 10, ни Windows 11. Версии компилятора и runtime фиксируются в логах.

Windows 10 x64 и Windows 11 x64 обязательны для Desktop. Qt 6.12 — последняя
официально поддерживающая Windows 10 ветка (в документации минимум 1809).
Первый готовый архив для ручной проверки — Windows x64: EXE, динамические Qt DLL,
QML-модули, плагины, app-local VC143 runtime и уведомления о лицензиях.
Проверять именно упакованную копию с очищенными путями разработчика, затем
отдельно на пользовательских ОС. Успех CI не означает приёмку платформы.

Linux пользователя: ALT Regular GNOME либо CachyOS GNOME/KDE. Совместимость
с библиотеками дистрибутива, Wayland и X11 проверяется позднее отдельно.
Сейчас пакет Linux для конечного пользователя не выбран.

Huawei nova 15 Pro / EMUI 15 — раннее целевое устройство. Не вводить обязательную
зависимость от GMS. Перед минимальным APK определить Android API Level и ABI;
наличие EMUI не доказывает их значения. Для Qt 6.12 ориентир — JDK 21,
NDK r27c (27.2.12479018); сейчас Android toolchain не устанавливается.
Затем исследовать фоновые ограничения и энергосбережение EMUI, экран блокировки,
медиакнопки и аудиофокус. Не откладывать первую проверку APK до готового Desktop.

Ручные проверки планируются с владельцем в доступные часы (Москва):
Windows 10 09:00–20:00, Windows 11 и Linux 21:00–01:00, Huawei постоянно.
Детали лицензий и ссылки на подтверждающие исходники — `docs/DEPENDENCIES.md`;
инструкции сборки и ограничения проверки окна — `docs/BUILD.md`.


## 14. Уточнения после прототипов 001-A, 001-B1 и 001-B2 — 29.10.2026

Результаты подтверждают отдельные сценарии, но не окончательный производственный выбор:

- Qt Multimedia с QMediaPlayer и FFmpeg декодировал пять синтетических локальных образцов; владелец подтвердил слышимый звук и управление на Windows 11.
- На Desktop прототип QMediaPlayer::setSourceDevice() с WebDavRangeDevice воспроизвёл потоковый FLAC через loopback mock; владелец подтвердил слышимый звук, паузу, seek и отказ при HTTP 200.
- Не проверялись реальный Cloud.Mail.ru, внешняя сеть, потоковое воспроизведение всех контейнеров, Android audio, gapless или точное потребление памяти всего стека.
- IPlaybackEngine и ICloudProvider пока не реализованы как production-контракты. LocalPlayback, WebDavProbe и WebDavRangeDevice — исследовательские компоненты.

Рекомендуется сохранить Qt Multimedia / QMediaPlayer кандидатом для следующего Desktop-среза за сменной границей IPlaybackEngine. Собственный PCM pipeline пока не начинать: к нему следует возвращаться только при измеренном недостатке Qt или обязательном требовании платформы. Это предложение, не окончательный выбор.

Возможности Range и валидатора сообщать как unknown/supported/unsupported, а не угадывать по Accept-Ranges. Только чтение; ошибки различают сеть, тайм-аут, отмену, авторизацию, лимит, смену версии и протокол. |
| IPlaybackEngine | Асинхронные команды play/pause/seek/stop для сессии, смена источника и события состояния, позиции, ошибки и готовности буфера. Движок принимает источник через отдельную абстракцию; UI не получает QMediaPlayer* напрямую. Идентификатор поколения предотвращает применение позднего ответа старого трека к новому. |
| Потоковый источник | Отдельный контроллер между provider и движком. Он владеет очередью запросов, ограниченным RAM-буфером, отменой устаревших запросов и проверкой версии. Не делать сетевой запрос из realtime-аудиоколбэка. Прототипный QIODevice — только адаптер, его синхронная блокировка не становится контрактом cloud-слоя. |
| Аудиокэш | Разделить краткоживущий ограниченный RAM-буфер/кэш диапазонов и постоянный дисковый кэш. Будущий ICacheStore отмечает офлайн-копию доступной только после проверки размера и версии. Частичный файл не становится offline-копией. |

Для склейки нескольких диапазонов требовать сильный ETag и If-Range либо другой доказанно эквивалентный механизм версии. Слабый или отсутствующий валидатор не позволяет безопасно объединять ответы. Поддержка Range неизвестна до пробного GET Range с проверкой 206, Content-Range, длины и стабильной версии.

### 14.2 Потоки, блокировки и медленная сеть

WebDavProbe обслуживает сетевые объекты в их Qt-потоке, ограничивает тело ответа, имеет таймер, отмену и ограниченные повторы для временных HTTP-ошибок. В WebDavRangeDevice кэш страниц защищён QMutex, но блокировка не удерживается во время сетевого запроса. Промах кэша вызывает BlockingQueuedConnection и ждёт сетевой ответ в потоке чтения. Чтение UI-потоком отклоняется. Это уменьшает риск зависания интерфейса, но медленная сеть может задержать поток декодирования до тайм-аута запроса (5 секунд в B2).

Возможные риски модели потоков, не наблюдавшиеся как сбой приёмочных сценариев: вызов readData из собственного worker-потока может создать самоблокировку; конкурентные read/seek одного QIODevice не закреплены контрактом; удаление объекта зависит от отмены активного reply и завершения worker. Мьютекс не удерживается на время сети, что снижает вероятность взаимной блокировки. Расширять модель следует только после явного single-reader владения или перехода к асинхронной выдаче.

Тесты задержки/отмены проверяют mock-сценарии, не реальные underrun при длинном RTT, jitter, потере пакетов и смене сети. Лимит 256 КиБ относится только к страницам адаптера: QMediaPlayer/FFmpeg могут удерживать дополнительные входные данные, пакеты и PCM. В B2 нет отдельного адаптивного prefetch, coalescing одинаковых запросов или доказанного поведения seek во всех backend.

Для дальнейшего прототипа рекомендуется bounded low/high-water буфер, приоритет текущего трека и seek, отмена старых запросов при seek/смене трека и понятное состояние «буферизация». Размеры буфера выбирать по измерениям на искусственных задержках и реальном целевом устройстве. Не обращаться к сети из аудиоколбэка.

При HTTP 200 вместо ожидаемого 206 поток прекращается. Рекомендуемый fallback — показать понятное сообщение и предложить отдельно выбранное скачивание во временный/дисковый кэш с прогрессом, квотой, отменой и проверкой версии. Автоматически скачивать целый трек под видом streaming нельзя.
