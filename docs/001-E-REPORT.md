# 001-E — потоковые форматы и устойчивость WebDAV

**Дата:** 30 октября 2026 года
**Основа:** `main` на `d2c599d16f177e5f232869c0e1ab89d0759a3888`; PR №10 объединён. Его post-merge Desktop CI run 40954984722 завершился успешно: documentation, Ubuntu/Linux и Windows Server jobs.
**Граница:** только синтетические CC0-файлы через локальный loopback mock `/AllMusic`; без Mail WebDAV, реквизитов, личной музыки, постоянного кэша, Android-аудио и собственного PCM pipeline.

## Вывод простыми словами

Задача расширяет проверку потокового прототипа: вместо одного FLAC проверяются MP3, FLAC, AAC-LC ADTS, AAC-LC M4A и ALAC M4A. Добавлены управляемые задержки, ограниченная скорость, временный обрыв, повторный запрос после восстановления, отмена и ответы HTTP 200/206/416. Все числа ниже относятся к синтетическим файлам и CI-машинам. PCM показывает, что декодер получил звук; он не подтверждает отсутствие слышимых щелчков или пауз на физических наушниках.

## Фикстуры и автоматическая проверка

Скрипт генерирует пять 8-секундных локальных образцов и пять 32-секундных потоковых образцов: MP3 128 кбит/с, FLAC 16 бит, AAC-LC 128 кбит/с в ADTS и M4A, ALAC 24 бит в M4A. Все сигналы — стерео 44,1 кГц, 440 Гц, без метаданных и пользовательского контента; M4A для streaming создаётся с индексом в начале файла.

Для каждого потокового образца тест требует ненулевой PCM до передачи всего файла, проверяет длительность, три перемотки, завершение около конца и предел кэша `WebDavRangeDevice` в 4 × 64 КиБ. Записываются время до первого PCM, проверенные Range payload-байты, размер файла, задержки seek, число HTTP-запросов, кэш адаптера и пиковый RSS процесса. Пиковый RSS относится ко всему тестовому процессу и не позволяет отделить память QMediaPlayer/FFmpeg.

Дополнительные сценарии проверяют задержку и темп выдачи данных, HTTP 429 с `Retry-After`, временный обрыв тела ответа и повторное открытие источника после восстановления; HTTP 200, 206 и 416; смену ETag; неполный ответ; повторные перемотки; отмену активного GET; пользовательский Stop, смену трека и уничтожение воспроизводящего объекта во время загрузки. Mock принимает только loopback и не проксирует запросы наружу.

В PR №11 Stop для сетевого источника теперь выполняется контроллером: он сначала отменяет активный `WebDavRangeDevice`, затем останавливает плеер и отсоединяет источник. Кнопка QML вызывает контроллер, а не `QMediaPlayer::stop()` напрямую. Для локального файла Stop сохраняет источник; повторный Play запускает его снова. Для остановленного сетевого трека Play открывает новый поток. Пауза и продолжение остаются отдельными действиями.

Это результаты `playback-streaming` в Ubuntu 24.04, Qt 6.12.0 / FFmpeg 9.0.1. Для каждого файла тест получил PCM до полного Range payload, трижды перемотал, дошёл до EndOfMedia и не превысил предел кэша 262 144 байта. Пиковый RSS всего тестового процесса по мере выполнения матрицы составил 69 513 216 байт (MP3/FLAC), 70 795 264 (AAC ADTS), 71 581 696 (AAC M4A) и 74 727 424 (ALAC M4A). Значения кумулятивны по процессу и не отделяют память плеера, FFmpeg, Qt и теста. Полный Qt/C++ прогон локально не запускался: исполнительное окружение не содержит CMake и Qt 6.12.0.

Linux Desktop run [40962934885](https://github.com/metravolokos/allmusic-player/actions/runs/40962934885) прошёл CTest 4/4: playback decode 9/9, потоковые тесты 24/24, WebDAV safety 86/86, window smoke. Windows CTest также прошёл 4/4; вывод QtTest в Windows логе агрегирован CTest и не показывает число внутренних QtTest assertions.

## Сетевые сбои и остановка

| Сценарий | Проверяемое поведение | Результат |
|---|---|---|
| HTTP 206 | Проверяются Content-Range, размер и сильный ETag; страницы попадают в кэш | Проходит |
| HTTP 200 вместо Range | Отказ без перехода к полной загрузке | Fail-closed, проходит |
| HTTP 416 | Отказ без кэширования страницы | Fail-closed, проходит |
| Изменение ETag / неполный ответ | Старая версия и частичное тело не принимаются | Fail-closed, проходит |
| Задержка и ограниченная скорость | 64-КиБ Range при искусственной задержке/темпе завершился за 342 мс | Проходит |
| HTTP 429 | Учитывается короткий Retry-After и повторяется тот же Range | Проходит |
| Временный обрыв / возврат сервера | Источник с обрывом завершается ошибкой; после восстановления новый источник читает успешно | Только повторным открытием; автоматического продолжения того же источника нет |
| Повторные seek | Четыре уникальные 64-КиБ страницы читаются корректно, повторный seek использует кэш | Проходит; кэш в тесте 262 144 байта |
| Отмена прямого Range чтения | Запрос отменяется во время активной загрузки | Проходит, быстрее 1,5 с |
| Пользовательский Stop во время GET | Mock задерживает Range GET на 2 500 мс; после Stop проверяется фактическое число активных ответов, затем повторный запуск выбранного сетевого трека | Активный ответ закрыт за 0 мс в Linux и за 2 мс в Windows; предел теста — 1 000 мс. Через 100 мс активных ответов по-прежнему 0; повторный Play отправляет новый Range GET |
| Локальный Stop и повторный запуск | Локальный синтетический MP3 останавливается и запускается снова | Источник остаётся выбранным, повторное воспроизведение проходит |
| Смена трека во время GET | Старый ответ отменяется, открывается второй трек | После исправления порядка cancel → stop: 0 мс, проходит |
| Уничтожение LocalPlayback во время GET | Плеер и источник завершаются без ожидания сетевого тайм-аута | После явной отмены в деструкторе: 0 мс, проходит |

В медленном сценарии ALAC M4A размером 3 335 185 байт сервер выдавал примерно 32 КиБ/с. Первый PCM пришёл через 2 197 мс после старта; при 131 072 полученных Range-байтах зарегистрирован максимальный интервал PCM callback 1 887 мс и один интервал длиннее 250 мс. Пиковый RSS процесса в этом сценарии — 69 513 216 байт. Это показатель подачи PCM в тест, а не доказательство фактической слышимой паузы или underrun устройства.

Первоначальная проверка обнаружила, что прямой `QMediaPlayer::stop()` не отменяет активный сетевой GET. В PR №11 это исправлено контролируемым порядком отмены и отсоединения источника. Автотест проверяет закрытие серверного ответа, а не только время возврата метода: медленный ответ исчезает из счётчика активных запросов за 0 мс в Linux и 2 мс в Windows, при естественной задержке 2 500 мс. Тест также проверяет повторный сетевой запуск, паузу/продолжение и локальный Stop с повторным запуском. Смена трека и уничтожение `LocalPlayback` во время активной загрузки проходят без ожидания сетевого тайм-аута; в CI зависаний, устаревших ответов или ошибок времени жизни объектов не обнаружено. Эти проверки не доказывают отсутствие гонок вне покрытых сценариев.

PCM callback gaps — только диагностический показатель. Он не равен underrun физического аудиовыхода и не используется для заявления «слышимых прерываний нет». Ручная проверка на Windows 11 описана в [WEB-DAV-STREAM-TEST.md](WEB-DAV-STREAM-TEST.md); её должен выполнить человек с наушниками или колонками.

## Windows 11 и CI

Существующий Desktop workflow сохраняет документационную проверку, Linux и Windows Server сборки, тесты, автономную упаковку и WebDAV regression kit. Портативный Windows x64 ZIP включает синтетические локальные и потоковые файлы, приложение, loopback mock, Windows launcher и инструкцию ручной проверки. Android workflow и состав APK не менялись.

Desktop run [40979576568](https://github.com/metravolokos/allmusic-player/actions/runs/40979576568) завершился успешно на Ubuntu 24.04 и Windows Server 2022. CTest прошёл 4/4 на обеих платформах. Linux: streaming 25/25, WebDAV regression 86/86; Windows: streaming 25/25 за 19,82 с, включая новые Stop/restart проверки, плюс playback decode, упаковка и window smoke. Отдельный Android APK run [40979576577](https://github.com/metravolokos/allmusic-player/actions/runs/40979576577) также успешен.

В промежуточных Windows прогонах `playback-streaming` несколько раз завершился Failed около 25 с. Добавленный текстовый отчёт QtTest выявил, что `transient429HonorsRetryAfter` видел первым чужой Range `bytes=131072-196607` от предыдущего медленного ALAC PCM сценария; следом шёл `bytes=0-65535` текущего теста. Тест сравнивал первые два запроса и ошибочно принимал этот отложенный запрос за первую попытку 429. Исправлены очистка активных источников и изоляция ответа 429 на уникальный путь и первый Range; тест требует повтор того же диапазона. Нулевая метрика первого PCM также защищена атомарным обновлением. Причина была в межтестовой изоляции и гонке метрики, не в декодировании форматов.

Переносимая сборка Windows x64 готова: [ZIP приложения](https://github.com/metravolokos/allmusic-player/actions/runs/40979576568/artifacts/12944333738) (около 81 МБ) и [комплект loopback WebDAV](https://github.com/metravolokos/allmusic-player/actions/runs/40979576568/artifacts/12944013414) (около 6,6 МБ). ZIP и комплект собраны и проверены в Windows CI; инструкцию ручной проверки на Windows 11 см. в [WEB-DAV-STREAM-TEST.md](WEB-DAV-STREAM-TEST.md). Физическая проверка на Windows 11 и подтверждение слышимого звука человеком ещё не проводились. CI подтверждает сборку и автоматические проверки, но не акустический результат.

Android APK workflow сохранён и завершился успешно в run [40979576577](https://github.com/metravolokos/allmusic-player/actions/runs/40979576577); [APK](https://github.com/metravolokos/allmusic-player/actions/runs/40979576577/artifacts/12944337867) опубликован. Это подтверждает, что изменение не сломало текущую сборку APK, но не проверяет Android-аудио.

## Ограничения и решение о следующем этапе

- Настоящий Cloud.Mail.ru, нестабильный внешний интернет, смена Wi-Fi/мобильной сети, аудиоустройства и слышимые прерывания здесь не испытываются.
- Максимум 256 КиБ относится только к кэшу страниц адаптера. Пиковый RSS процесса и внутренние очереди Qt/FFmpeg дают лишь грубую оценку.
- Адаптер ждёт полный ответ диапазона в потоке чтения; искусственная сеть показала длинные интервалы PCM callback при недостаточной скорости. Автотесты не превращают прототип в production-потоковый API.
- Клиент и mock этой задачи ограничены loopback и обязательным маркером тестового сервера. Они сами по себе не готовы подключаться к реальному WebDAV.

Итог: пять форматов прошли PCM / seek / завершение на Linux CI; сетевые проверки mock, включая пользовательский Stop с фактической отменой GET и повторный запуск, прошли на Linux и Windows. В протестированных сценариях блокирующих проблем остановки, смены трека или уничтожения источника не осталось. Прототип всё ещё не готов прямо подключаться к Cloud.Mail.ru: проверка принимает только локальный mock, автоматическое продолжение того же источника после сетевого обрыва не реализовано, а слышимый звук и аудиопрерывания на Windows 11 должен проверить человек. Следующим шагом может быть только отдельно утверждённая ограниченная read-only проверка реального WebDAV после решения владельца; она не выполнялась в 001-E. D-028 и D-029 остаются предложениями, окончательная архитектура не утверждается.
