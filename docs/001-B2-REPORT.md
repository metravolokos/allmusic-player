# 001-B2 — отчёт потокового прототипа WebDAV

## Объём и реализация

Ветка `task/001-b2-webdav-stream`, создана от объединённого PR #8 (`b2232ff`).
Используется только локальный тестовый сервер на loopback и путь `/AllMusic`.
Запросы — PROPFIND и GET; запрещённые методы сервер отклоняет. Нет реальной
авторизации, реального Cloud.Mail.ru, постоянного аудиокэша, медиатеки, Android
audio или gapless.

`WebDavRangeDevice` представляет файл как seekable QIODevice, который передаёт
запросы через существующий `WebDavProbe` на отдельном потоке Qt Network. Размер
и сильный ETag берутся из PROPFIND. Каждый диапазон проверяет 206,
Content-Range, длину и тот же ETag через If-Range. Клиент принимает только
`127.0.0.1`, `/AllMusic` и специальный маркер mock `001-B2-loopback`; редиректы
запрещены. Если сервер возвращает 200, запрос прерывается, файл не принимается
как потоковый и полная загрузка не начинается.

Размер страницы — 64 КиБ; одновременно в кэше адаптера не более четырёх страниц
(256 КиБ). Транспорт также ограничивает отдельный ответ 64 КиБ. Память внутри
Qt Multimedia/FFmpeg не имеет публичного точного лимита; она оценивается
косвенно по числу переданных Range-байтов к первому PCM. Аудиокэш на диск не
создаётся. Чтение из UI-потока прерывается с ошибкой, чтобы не замораживать
интерфейс.

## Фикстуры и автоматические сценарии

Пять B1 тестовых тонов (MP3, FLAC, AAC-LC ADTS/M4A, ALAC M4A) синтетические,
CC0. Для сетевого запуска добавлен отдельный 32-секундный FLAC. Личной музыки
нет.

Автотесты проверяют PROPFIND → ETag → If-Range, 206/Content-Range, чтение
отдельного диапазона после seek, ранний PCM, тайминг/переданные байты, 256-КиБ
лимит кэша, HTTP 200 fallback, неожиданный loopback сервер, изменение ETag,
оборванный ответ, отмену запроса и последующее восстановление с новой версией.
Вывод PCM отделён от слышимого физического звука.

## Результаты

Локальный executor не содержит Qt/CMake, поэтому C++ сборка и QtTest проходят
только через GitHub CI. В первом прогоне Desktop `40942046920` CMake собрал
приложение, WebDAV-модуль, mock и `WebDavRangeDevice`, но компиляция нового
`streaming-tests` остановилась: требовался явный `#include <QAudioBuffer>`.
Include добавлен; повторный CI для исправленного head ожидается. CTest и
измерения в первом прогоне не запускались.

| Проверка | Результат |
|---|---|
| Linux / Qt 6.12.0 / CTest, включая `playback-streaming` | Первый прогон остановился на compile error теста; исправление ожидает проверки |
| Windows Server / Qt 6.12.0 / CTest и Windows x64 архив | Ожидается повторный CI |
| Android APK / строгий регрессионный аудит | Ожидается |
| Windows 11: слышимый звук, управление, seek и HTTP 200 fallback | Требует ручной проверки владельца |

Метрики первого PCM, валидных Range payload-байтов до PCM, размеров фикстуры и
кэша будут занесены по тестовому логу. Эти значения описывают декодирование,
не слышимый звук. Ручной сценарий: [WEB-DAV-STREAM-TEST.md](WEB-DAV-STREAM-TEST.md).

## Решение по архитектуре

`QMediaPlayer::setSourceDevice()` остаётся экспериментальным кандидатом; D-008,
D-009 и D-027 не считаются окончательно решёнными. Если CI не подтвердит ранний
PCM/seek вне загруженной области или UI-поток блокируется, потоковый режим не
объявлять готовым. Варианты для владельца: (1) собственный FFmpeg demux/decode
с подачей PCM в QAudioSink — высокий объём и риск сопровождения; (2) ограниченно
загружать текущий файл во временный файл и разрешать seek после загрузки — проще,
но это не streaming; (3) выбрать отдельный аудиодвижок с документированными
асинхронными Range-контрактами — средний/высокий объём интеграции. В таком случае
нужно отдельное архитектурное решение владельца.

## Ограничения и приёмка

Mock-сервер и клиент принадлежат одному тестовому процессу в автоматических
проверках; Windows архив дополнительно предоставляет отдельный loopback
`webdav-mock.exe` и launcher. Автотесты не доказывают слышимый звук. Windows 11
остаётся основной ручной ОС по D-026. PR не означает приёмку; объединение не
выполнять до решения владельца.
