# Постоянный режим автономной разработки AllMusic Player

**Решение владельца от 2026-11-01.** С этого момента отдельное одобрение каждого небольшого Issue, промежуточного PR или следующей задачи в GitHub **не требуется** при соблюдении правил ниже. Это заменяет старые процессные фразы «ждать решения владельца перед каждой задачей», но **не отменяет** техническое ТЗ, устройство проекта, реальные аппаратные испытания или ограничения безопасности.

## Приоритет источников

`SPEC.md`, `ARCHITECTURE.md`, `ROADMAP.md`, `DECISIONS.md`, `AGENTS.md` и текущие GitHub Issues/PR. Если исторические разделы ROADMAP требуют разрешения на каждую задачу, для небольших работ *в пределах принятого ТЗ и текущей стадии* действует настоящее постоянное разрешение. Спорные изменения продуктовых требований и ключевых решений всё ещё требуют содержательного вопроса владельцу в чате, но не нажатия Approve в GitHub.

## Делать без отдельного согласования

1. Инвентаризация текущей ветки/HEAD, открытых PR, проваленных CI и уже запланированных задач; не повторять выполненную работу.
2. Одна небольшая задача из утверждённого ТЗ за раз: документация/критерии приёмки, контрактные и mock-тесты, локализованная регрессия без расширения доступа, небольшое исправление в уже принятой архитектуре.
3. Для неё — фиксированный `task_id`, ссылка на Issue, ожидаемый base SHA, отдельная ветка, diff, фактические тесты, объяснимые результаты, PR на русском, актуализация STATUS/DECISIONS.
4. Исследование кандидатов из параллельных AM-D/AM-L: рассматривать **проверенные идеи и негативные тесты**, а не слепо копировать чужой исходный код; в целевом репозитории иметь собственные тесты.
5. После подтверждённого успеха — готовить следующую независимую задачу дорожной карты без ручного GitHub Approve.

## Слияние без ручного GitHub Approve: только строго проверенные PR

Разрешён **автоматический merge ограниченного малорискового PR**, если:
- он соответствует конкретному утверждённому Issue и единственной активной рабочей ветке; он не draft и имеет неизменный проверенный HEAD SHA;
- точный `git diff` и список изменённых файлов проверены независимо; нет незакрытых замечаний, конфликтов и неожиданных правок;
- **все требуемые для затронутого кода проверки CI**, привязанные к этому HEAD, фактически завершились успешно; отсутствие/неполнота CI не считается успехом;
- GitHub branch protection/review requirements соблюдены; не включать слепой `auto-merge`, который может сработать без обязательных checks, не снимать защиту `main`;
- отсутствуют новые зависимости, изменения архитектуры, security/TLS/Range/ключей/доступа, WebDAV записи, JNI/Media3, миграций БД, релиза/пакетирования, CI workflows, `AGENTS.md`, лицензионных документов и риски потери пользовательских данных;
- непроверенная ручная приёмка не является необходимым доказательством именно для этого PR;
- непосредственно перед merge повторно подтверждены base/head/CI и передан `expected_head_sha`. При сомнении — BLOCKED, не merge.

Нельзя автоматически сливать PR с новой слышимой функциональностью воспроизведения/seek, изменениями Android background, сетевым протоколом, криптографией или релизом **только** на основании зелёного CI. Владелец не обязан нажимать Approve, но необходимую ручную проверку приложения продолжает выполнять и фиксирует результат.

## Не делегировано

- Изменение объёма первой версии или основных архитектурных решений без содержательного согласования.
- Доступ к реальным Mail/WebDAV паролям и медиатеке; любые HTTP-записи на сервер.
- Подмена защищённых тестов, отключение CI, обход branch protection, force-push и несанкционированные релизы.
- Запуск нового платного API или нового облачного окружения.
- Автоматическое использование исходников параллельного проекта без совместимости и тестов.

## Работа планировщиков и фактическое исполнение

Отдельный почасовой Codex/ChatGPT монитор может составлять задания, сравнивать PR и сообщать о результатах, **но сам не является Codex Cloud средой для C++/Qt сборок**. До появления поддерживаемого first-party облачного запуска задачи разработки в опубликованной Codex Cloud среде начинаются через существующий Codex Cloud UI. Это остаётся единственным необходимым ручным *стартом задачи*, если агент не имеет другого подтверждённого исполнения. Не притворяться, что Github Issue запустил cloud task.

## Первая автономная очередь

1. [Issue #12](https://github.com/metravolokos/allmusic-player/issues/12): исключительно обновление документации «Избранное/плейлисты», без production-кода; сначала проверить, что требование ещё не отражено в актуальном SPEC.
2. После неё — одно read-only сравнение SEL-009/SEL-010 и проверки существующих negative tests. Сначала подтвердить, что аналогичный fix ещё не включён в `main`.
3. Затем небольшие этапы из ROADMAP по зависимостям и существующей принятой архитектуре; ограниченный WIP=1.

Не выдавать по одному и тому же модулю две конкурирующие ветки, не расходовать CI на повторную проверку без изменений.
