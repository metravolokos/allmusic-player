# Проверка Cloud Mail WebDAV — 002-B

Инструкция для владельца Windows. Для проверки не нужны Qt, CMake, Visual Studio,
Python или доступ к исходному коду. Приложение пока только проверяет подключение
и небольшой диапазон одного выбранного файла; воспроизведение из облака не входит.

**Результат ручной проверки владельца на Windows 11, 30.10.2026:** авторизация
и просмотр `/AllMusic` успешны, показано 3590 непосредственных элементов.
Отдельная проверка Range одного FLAC пока **не подтверждена**: приложение сообщило
об ошибке формата/диапазона. Для разбора не передавались пароль, имена файлов или
реальные значения HTTP-заголовков. Этап 002-B не считается принятым до успешной
ручной Range-проверки.

## Перед запуском

Создайте в настройках аккаунта Mail отдельный **пароль внешнего приложения**
для AllMusic Player. Обычно это раздел безопасности аккаунта → пароли для
внешних приложений. Если расположение пункта изменилось, используйте официальную
[справку Mail WebDAV](https://help.mail.ru/cloud/desktop/webdav/). С 2022 года
для WebDAV нужен пароль внешнего приложения, а не основной пароль почты.

У такого пароля на стороне Mail могут быть права записи. Приложение ограничивает
свои запросы методами чтения `PROPFIND` и `GET`, но это **не гарантирует**, что
сама учётная запись или пароль являются read-only. Не используйте пароль, которым
не готовы авторизовать это приложение.

## Скачать Windows ZIP без средств разработки

1. Откройте PR 002-B в GitHub и дождитесь зелёных обязательных проверок Desktop
   и Android.
2. В GitHub откройте **Actions** → **Desktop foundation** → **Run workflow**.
3. Укажите ветку PR в `source_ref` — `codex/002-b-cloud-webdav`. Включите
   `windows_zip=true` и `full_tests=true`; `webdav_test_kit` оставьте выключенным.
   Так один запуск проверит Desktop на Linux и Windows, затем упакует Windows ZIP.
4. Дождитесь зелёного `Desktop CI result` и скачайте артефакт
   `AllMusicPlayer-Windows-x64-…` этого запуска.
5. Распакуйте ZIP в отдельную папку и запустите `allmusic-player.exe`. Qt и
   компилятор на компьютере не нужны. Не удаляйте DLL, папки и лицензии из ZIP.

Если Windows блокирует неподписанное приложение, не отключайте защиту. Сообщите
только текст предупреждения и ссылку на скачанный GitHub-запуск.

## Проверить каталог

1. В окне **«Диагностика Cloud Mail — только чтение»** введите адрес почты и
   пароль внешнего приложения. Поле пароля скрывает ввод.
2. Нажмите **«Проверить подключение»**. Эта кнопка отправляет один `PROPFIND`
   с `Depth: 1` только к `/AllMusic/`. До нажатия приложение не обращается к
   Cloud Mail.
3. Дождитесь статуса и количества непосредственных папок и аудиофайлов.
   Приложение не обходит подпапки, не сканирует весь аккаунт и не создаёт
   отсутствующую `/AllMusic`.
4. Если появилась ошибка `404`, остановитесь: проверьте наличие `/AllMusic`
   самостоятельно в Облаке Mail. Приложение не будет искать или создавать папку.
5. Во время запроса можно нажать **«Отменить»**. Нажмите **«Отключиться»**, чтобы
   очистить список и завершить временную сетевую сессию. Учётные данные не
   сохраняются в настройках и удаляются из сессии при отключении или закрытии
   приложения.

## Необязательная отдельная проверка Range

1. Выберите один аудиофайл верхнего уровня в списке `/AllMusic`.
2. Отдельно отметьте согласие на запрос до 64 КиБ и нажмите **«Проверить Range»**.
   Выбор элемента сам по себе запрос не отправляет.
3. Успех означает, что получен HTTP `206`, фактическое число байтов совпало с
   диапазоном в `Content-Range`, а кодирование тела не меняет байты. По RFC 9110
   `Content-Length` может отсутствовать: тогда принимается только ответ, для
   которого Qt Network корректно определил границу сообщения, а размер тела
   совпал с `Content-Range`. Если `Content-Length` есть, он должен совпасть с
   размером диапазона и тела. Если размер файла известен, запрашивается
   `bytes=0-(min(65536, размер)-1)`; при сильном ETag отправляется `If-Range`.
4. HTTP `200` считается неподдержанным Range. Ответ останавливается, целый файл
   не скачивается и не воспроизводится. Переадресации и ошибки TLS не обходятся.
5. При ошибке интерфейс показывает HTTP-статус, категорию проверки, наличие
   `Content-Range`, `Content-Length`, `Transfer-Encoding`, `Content-Encoding` и
   ETag, числовые границы/размер диапазона и число полученных байтов. Сами значения
   заголовков, имя/путь файла и тело ответа не показываются.

## Что безопасно сообщить владельцу проекта

Достаточно написать вручную:

- получилось ли проверить каталог;
- количество показанных непосредственных элементов;
- результат отдельной Range-проверки: HTTP `206`, `200` или категория ошибки;
- наличие `Content-Length`, числовые границы диапазона и число полученных байтов;
- ETag: отсутствует / слабый / сильный и был ли отправлен `If-Range` (само значение
  не присылать).

Не отправляйте адрес почты, пароль, названия файлов и папок, URL, заголовки,
сырые логи, снимки окна или содержимое медиатеки. Можно поделиться только
обезличенными итогами выше.

**Codex и CI не подключались к Облаку Mail.** Владелец подтвердил успешные
авторизацию и просмотр каталога, но Range пока не подтверждён. Следующую проверку
владелец выполняет на своём компьютере после скачивания новой сборки.

## Второе испытание и классификация Content-Range

Повторный тест владельца на Windows 11, сборка `ace4b9b` из
[CI 41086647415](https://github.com/metravolokos/allmusic-player/actions/runs/41086647415):
HTTP 206, Content-Length и тело 65536 байт, Content-Range присутствует, но
не распознан. Это **не доказывает корректность диапазона**. Точная причина
по обезличенному отчёту пока неизвестна; новый код не объявляет её установленной.

Сопоставление с [RFC 9110 §14.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-14.4):
для bytes ожидается `bytes SP first-last/(число или *)`; `bytes=...` — синтаксис
запроса Range, а не Content-Range. Неизвестный unit, `*/число` в HTTP 206,
списки/повторённые поля, знаки/нечисловые части и переполнение не дают пригодного
частичного диапазона. Возможные причины — ответ сервера/посредника в другой
конструкции, повторённое поле, непечатаемые символы или слишком большое число.
Это гипотезы, ни одна пока не подтверждена на Cloud Mail.

`rawHeader()` Qt возвращает значение поля; повторения могут быть объединены.
Клиент дополнительно проверяет `rawHeaderPairs()` без учёта регистра имени,
отклоняет повторённые поля, даже одинаковые, и значения с запятой. Классификатор
ограничен 256 байтами до регулярных выражений/числовых преобразований. Он выдаёт
только заранее заданные категории: длина до/свыше предела, unit bytes/другой,
разделитель пробел/табуляция/равно/отсутствует или иной, числовая/иная конструкция,
неудовлетворимый диапазон, переполнение qint64, повтор/объединение,
непечатаемые или не-ASCII символы. Ни один фрагмент исходного поля не включается.
Ограничение относится к анализу значения, а не к общему сетевому буферу Qt.

Принимаются только однозначные bytes-диапазоны: регистр unit несущественен,
краевые HTTP OWS и несколько обычных пробелов допустимы; внутренние табуляции,
`=`, CR/LF и другие управляющие символы не принимаются. Ранее использованное
`\\s+` было шире HTTP SP; теперь оно сужено. Семантические проверки границ,
размера, ETag/If-Range, framing и фактического тела остаются обязательными.
HTTP 206 и совпадение длины сами по себе недостаточны. Playback не запускается.

После нового зелёного CI и получения ZIP повторите отдельную Range-проверку
на Windows 11. Перепишите вручную **категорию синтаксиса**, HTTP-статус и результат
проверки; не присылайте заголовки, скриншоты, URL, ETag, пароль или имена файлов.
При отказе 002-B остаётся непринятой: понадобится исследование выявленной
категории на синтетическом mock, без автоматического допуска нового синтаксиса.

## Третье испытание и совместимость Cloud Mail (30.10.2026)

На проверенной Windows-сборке из [CI #97](https://github.com/metravolokos/allmusic-player/actions/runs/41116953856),
commit `deadd006`, владелец получил HTTP 206 и ровно 65536/65536 байт.
Безопасная классификация установила: unit `bytes`, **разделитель `=`**,
числовые начало/конец и числовой полный размер; `Content-Length=65536`,
`If-Range` отсутствует. Личные имена файлов и исходные значения заголовков не
сохраняются в GitHub. Клиент отклонил ответ из-за нестандартного разделителя.

RFC 9110 §14.4 требует `Content-Range: bytes SP first-last/total`, то есть
`bytes=...` в ответе формально некорректен. В **отдельном клиенте Cloud Mail**
введена *строго ограниченная совместимость* ровно с `bytes=first-last/total`,
где все три числа десятичные и находятся в диапазоне qint64. `bytes=.../*`,
лишние пробелы после равно, повторённые поля, списки, иные unit и непечатаемые
символы по-прежнему отвергаются. Сохраняются HTTP 206, контроль начала и конца
запрошенного диапазона, полного размера из PROPFIND, фактического размера тела,
Content-Length, допустимого кодирования, ETag/If-Range и лимита 64 КиБ. Старый
loopback-клиент, Android и потоковое воспроизведение не затронуты.

**Изменения пока не проверены C++/Qt CI и настоящим Cloud Mail.** До нового
успешного Windows/Linux CI и ручной Range-проверки 002-B не принята. Для ZIP
запустить Desktop foundation с `source_ref=codex/002-b-cloud-webdav`,
`full_tests=true`, `windows_zip=true`, `webdav_test_kit=false`.
