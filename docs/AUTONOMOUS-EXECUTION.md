# Автономное сопровождение AllMusic Player — решение владельца 01.11.2026

**Статус:** разрешён ограниченный автономный процесс по действующему `SPEC.md`, `ROADMAP.md`, `ARCHITECTURE.md` и `DECISIONS.md`. Цель: не требовать от владельца GitHub-клика на каждый небольшой PR. При противоречиях настоящих правил и прежних указаний про ручное согласование *каждой* стадии/PR действует это более позднее решение, но **не** снимает требования о фактическом тестировании, защите веток и ручной приёмке устройств.

## Право действовать без дополнительных подтверждений

- Составлять план очередного **небольшого** шага внутри уже согласованного продуктового объёма; реализовывать документацию, проверки, ограниченные исправления в отдельных PR. До расширения фактических прав в исполнителе — работать только в разрешённом ему подмножестве.
- Готовить отдельный PR для каждого Issue/небольшого завершённого изменения, отчёт на русском, точные команды и исходные SHA.
- Независимый координатор может принять и через GitHub merge API объединить **только** PR низкорискового класса A после всех проверок, описанных в приватном [координационном регламенте](https://github.com/metravolokos/allmusic-coordination/blob/main/docs/AUTONOMOUS-DEVELOPMENT.md). Для исполнителя без доступа к hub обязательны минимальные правила ниже. Если реальная проверка CI невозможна, НЕ сливать.
- Не нужно отдельное согласование выбора каждого подпункта утверждённого `ROADMAP`, если не нарушается архитектура и нет нового продуктового решения; реальную приёмку на Windows/Huawei/Linux не подменять автоматическими тестами.

## Слияние PR класса A: минимум

1. PR не draft; ровно одна одобренная задача; ни одного секретного или чувствительного файла; база `main`, автор и source SHA идентифицированы.
2. Перед слиянием проверены полный diff, отсутствие опасных изменений, отсутствие существующей конфликтующей работы и сохранение `main` protection. Не нажимать или обходить admin bypass.
3. На **том же head SHA** обе отдельные GitHub Actions `Desktop foundation` и `Android Media3 002-D-M3` завершились `success` для данного PR (или иной заранее утверждённый, актуальный набор проверок; недоступность или пропуск — stop). Никаких «зелёных» статусов на прошлых SHA или только на main.
4. Задокументировать точные ограничения проверок и непроверенные устройства. Независимый координатор публикует `AUTO_REVIEW_OK` с PR/SHA/CI, затем только `merge_pull_request` с `expected_head_sha`; повторно не сливать.
5. Если защитные правила GitHub требуют отдельного review, нет соответствующих прав, CI/mergeability неизвестны или PR затрагивает класс B/C — остановиться с `BLOCKED`. Штатный GitHub Auto-merge здесь не включён, обходить защиту запрещено.

Класс A: документация, не меняющая безопасность или правила проекта; точечные регрессионные тесты и незначительные исправления существующего поведения после подтверждённой CI. В текущем пилоте Codex-автоматизация ограничена **документами Issue #12**; тесты/код пока не разрешены ей.

## Стоп-условия — никакого автоматического merge

- Изменения в `AGENTS.md`, `ROADMAP.md` с изменением правил процесса, `SECURITY.md`, `.github/**` или сетевой безопасности.
- Реальный WebDAV, TLS, реквизиты, Range и отмена сетевых запросов, все механизмы записи/удаления, новые сторонние зависимости и изменения лицензий.
- Изменение архитектуры/движка, БД/схемы пользовательских данных, Android package/runtime, release и сборки требующие слышимой приёмки.
- Переопределение `SPEC.md` сверх решений владельца; новые пользовательские функции, не утверждённые в ТЗ.
- Любые слития с красным/неизвестным CI, неопределённым статусом GitHub, изменившимся SHA, незакрытым вопросом о совместимости или отсутствии необходимого устройства.

Для B допускается подготовка ветки, draft PR и CI, но продуктовую приёмку владелец выполняет на устройстве и сообщает результат **в чате**; отдельные GitHub-одобрения не требуются. Класс C (релизы, секреты, прямое изменение protected main, API billing, новый cloud runner, операция записи в реальный WebDAV) требует отдельного явного решения.

## Cross-project evidence

Независимые проекты: `metravolokos/allmusic-deepseek` и локальный AllMusic-Mail-Local. Сравнивать **проверенные технические решения**, не авторитет модели. Реестр кандидатов `metravolokos/allmusic-coordination/registry/INTEGRATION.md`. Для переноса сначала подтвердить источник (SHA/дата/платформа), тесты и негативные случаи, затем создать отдельное Issue и воспроизвести решение архитектурно корректным способом. Нельзя слепо копировать чужой код или считать `LOCAL_TESTED` доказательством CI/проверки на Huawei.

Первыми рассматривать риски `QIODevice::bytesAvailable` для потокового буфера (`SEL-009`), строгость разделителей `Content-Range` (`SEL-010`) и проверку реальных диапазонов seek (`SEL-008`); они НЕ дают права менять сетевую безопасность или сливать изменения без отдельного review.

## Текущий пилот AM-C

Первая автономная задача — **только документационное** [Issue #12](https://github.com/metravolokos/allmusic-player/issues/12), потому что владелец уже одобрил избранное и простые локальные плейлисты для версии 1.0. Исполнитель вправе создать отдельную ветку и PR; не затрагивать код, не начинать реализацию плейлистов и не смешивать с Android/Cloud Mail. Координатор может принять пилотный PR только после всех условий класса A и строгого CI.

Текущие возможности планировщика Codex основаны на GitHub connector, **не** на подтверждённом unattended создании Codex Cloud jobs. Для полноценного выполнения тяжёлых C++ задач в Codex Cloud пока нужен отдельный реальный механизм запуска; не маскировать отсутствие запуска отчётами о мониторинге.
