# Проверки и артефакты GitHub Actions

CI проверяет изменения проекта. Он не производит готовые ZIP и APK при каждом PR.

## Какие проверки запускаются

Оба workflow запускаются для каждого PR в `main`, для push в `main`, при ручном запуске и при опубликованном релизе. Фильтров `paths` на уровне workflow нет: это оставляет стабильные итоговые статусы проверок даже для документации.

Первый шаг сравнивает точные SHA веток и классифицирует изменённые файлы. Лёгкая Desktop CI-проверка всегда проверяет документы и запускает все unit tests из `tests/ci`, в том числе для docs-only PR. Компиляция для Markdown-изменений не запускается. Для Desktop-кода запускаются сборка и тесты Linux и Windows; FFmpeg и синтетические аудиофайлы устанавливаются и создаются только для этих проверок. Для Android-кода выполняются Android unit tests, сборка APK и аудит его содержимого. Общие CMake-изменения проверяются на Desktop и Android. Изменения упаковки запускают только затронутую проверку комплекта.

Сценарий сравнения Git, неизвестное расширение, пустой результат или ошибка классификатора не могут пропустить сборку: при сомнении включаются Linux, Windows, Android и проверки Windows-комплектов. Тесты политики классификатора находятся в `tests/ci/`.

Итоговые статусы workflow называются **`Desktop CI result`** и **`Android CI result`**. GitHub API подтверждает, что `main` защищена и оба этих контекста обязательны. Они падают, если классификатор не отработал или ожидаемая платформа была пропущена/не прошла. Владелец включил только merge через PR, обязательное обновление ветки перед слиянием и запрет обхода правил, force push и удаления `main`.

## Повторная проверка `main`

GitHub API для публичного репозитория подтверждает `main.protected: true` и обязательные контексты `Desktop CI result` и `Android CI result`. Endpoint детальных branch protection settings остаётся недоступен GitHub-интеграции, поэтому настройки запрета прямого push/обхода, удаления и требования актуальной ветки сверены с владельцем. Rulesets не используются; включена classic branch protection.

PR сравнивается с текущими SHA базовой и исходной веток. Обязательные проверки запускаются на merge-снимке PR. Если `main` продвигается после проверки, требование актуальности ветки не позволяет объединить устаревший результат: PR нужно обновить, после чего проверки запускаются заново. Прямые push, force push и обход защиты запрещены.

После объединения проверенного PR push в `main` запускает только лёгкие проверки: контроль документов и все тесты `tests/ci`. Linux/Windows/Android компиляция, FFmpeg, фикстуры и упаковка не повторяются, потому что защищённая `main` принимает только PR с обоими обязательными статусами и актуальной базой.

Классификатор fail-closed сохраняет полный набор платформенных проверок, если push не относится к `refs/heads/main`, отсутствует корректная пара SHA `before..after`, diff пуст или не читается, либо обнаружен неизвестный тип файла. Выпущенный релиз по-прежнему проходит полные проверки и упаковку; ручной запуск использует только явно выбранные проверки и артефакты. Политика лёгкого post-merge запуска предполагает, что владелец сохраняет перечисленные правила защиты `main`; при изменении настроек её нужно пересмотреть.

## Ручная упаковка

1. Откройте **Actions** и выберите **Desktop foundation** или **Android 001-C**.
2. Нажмите **Run workflow**. В поле `source_ref` введите имя ветки PR до объединения, например `ci/opt-001`. Таким образом код выбирается именно из указанной ветки, даже если сам workflow запущен со страницы `main`.
3. Для Windows отметьте `windows_zip`, `webdav_test_kit` или обе опции. Для APK откройте Android workflow и отметьте `android_apk`. При необходимости можно включить `full_tests`.
4. Скачайте артефакт со страницы запуска. Отчёт запуска и файл `BUILD-INFO.json` внутри комплекта содержат полный commit SHA исходников.

Android-проверка и без публикации скачиваемого результата компилирует APK, проверяет manifest, подпись и выравнивание, ABI, зависимости и лицензии. APK загружается как Actions artifact по ручному флажку или для релиза; отдельные разрешённые Android feasibility PR могут иметь узкое условие сохранения артефакта для проверки владельцем. В этой задаче исключение ограничено веткой `codex/002-d-android-cloud`. ZIP и WebDAV test kit публикуются только по ручному запросу или релизу. Изменение соответствующего сценария упаковки может создать временный архив внутри PR для его проверки, но PR-архив не загружается.

Опубликованный GitHub Release запускает полные проверки Desktop и Android и загружает все три комплекта как Actions artifacts на 90 дней. Windows ZIP сохраняет FFmpeg и Qt лицензионные материалы; WebDAV kit независимо собирает Qt Base и Qt Declarative уведомления. APK сохраняет Qt, NDK и включённые Java notices. Проверки лицензий не отключены.

## Кэши

| Кэш | Что хранится и как меняется ключ | Почему выбран |
|---|---|---|
| Qt Desktop | Кэш `install-qt-action`; префикс проекта и параметры Qt 6.12.0, ОС, архитектура, модули, `aqt` и URL установки входят в ключ | Повторная установка Qt занимала примерно 0,97–2,13 минуты на Desktop runner. При промахе действие само устанавливает закреплённую версию. |
| Qt Android + host tools | Только каталоги Qt 6.12.0 для Android arm64-v8a и Linux host tools; ключ включает обе архитектуры, выбранные архивы и commit закреплённого `aqt` | Установка Qt/aqt в исходном Android run занимала около 1,15 минуты. После восстановления проверяются `qmake` и точная Qt-версия. |
| Ninja | Только собранный бинарный файл 1.12.1; ключ включает ОС, архитектуру, компилятор и commit исходников | Сборка Ninja ранее занимала около 0,70–1,35 минуты; при miss он собирается из закреплённого SHA. |
| Python pip и aqt | `setup-python` кэширует pip downloads; Android workflow отдельно кэширует wheel форка `aqtinstall` с ключом по его закреплённому commit | Это не кэширует Python или установочные секреты; кэшируются повторно скачиваемые колёса и один закреплённый wheel. |

Кэш не содержит Gradle home, Android SDK/NDK, signing files, секретов, токенов, ключей или пользовательских данных. SDK/NDK занимали около 0,77 минуты установки вместе; размер и цена переноса не оправданы без измеренной чистой выгоды. Gradle home намеренно одноразовый, в нём могут находиться временные материалы debug-подписи. Загрузка Gradle wrapper и аудит зависимостей ранее были короткими; переносить весь Gradle-каталог нецелесообразно.

Изменения самих workflow или классификатора запускают отдельную короткую проверку тёплого кэша после обычной сборки. Она требует восстановления кэша, проверяет версии Qt, Ninja, CMake и Android `aqt` wheel, но повторно не компилирует приложение. Если кэша нет, основная сборка должна продолжить установку с нуля.

## Измерения

Исторический baseline снят с GitHub Actions runs до изменения workflow. Семь merge-повторов на `main` после уже успешного Desktop PR израсходовали 69,06 фактических runner-минут: 7 Linux jobs и 7 Windows jobs. С учётом коэффициента Windows 2x это 113,88 эквивалентных минут. Защищённая `main` теперь позволяет отключить эти повторы после merge CI-OPT-001; потенциальная экономия такого же числа повторов — 69,06 / 113,88 минут, пока прогнозная, так как PR ещё не объединён.

Два исторических PR только с Markdown запустили тяжёлые Desktop jobs на 20,37 runner-минут (33,92 эквивалентных минут с Windows 2x). Это историческая потенциально устранимая работа, а не уже сэкономленные минуты. Новая схема ожидает один лёгкий документный job; его фактическое время следует снять с первого docs-only PR.

В двух сохранённых Desktop artifacts исторически было около 90,43 MB на запуск при сроке хранения по умолчанию 90 дней (до 16,3 GB-дней в сумме, если оба оставались весь срок). Новые PR-запуски не загружают готовые ZIP/APK, диагностика сохраняется только при ошибке на 3 дня, временные аудио fixtures — на 1 день. Ручные артефакты хранятся 14 дней, релизные — 90 дней.

## Фактический запуск после изменения

На коммите `f3746804dedf285e4961238e7c6feef3ff6525df` завершились оба workflow: Desktop Linux/Windows, Android APK и аудит лицензий, проверки комплектов, cache-validation и итоговые статусы `Desktop CI result` / `Android CI result` — успешно. Сумма длительностей всех jobs составила **18,59 runner-минут**, или **25,96 эквивалентных минут** с коэффициентом Windows 2×. Это время выполнения jobs по логам; округление биллинга GitHub может дать другое число.

В этом прогоне Qt Desktop cache был найден на Linux и Windows (восстановлены архивы 387 MB и 505 MB). Кэш Ninja на обоих Desktop runners был холодным. Кэши Android wheel `aqtinstall`, Qt Android и Ninja тоже были холодными; установка прошла, APK собрался, а следующий warm-check успешно восстановил все три кэша и проверил CMake 3.30.5. Это проверило холодную установку Android Qt/aqt/Ninja и тёплое восстановление. Холодная установка Qt Desktop не проверялась: на этих runners уже был доступен кэш. У `setup-python` pip cache также был hit, поэтому установка CMake без pip cache отдельно не измерялась.

Обычный PR не сохранил Windows ZIP, WebDAV kit или Android APK. Изменённый сценарий WebDAV прошёл проверку комплекта, но его загрузка была пропущена. Android APK был собран и проверен, но не загружен. Единственный artifact этого полного PR run — синтетические аудио fixtures, 2,51 MB, срок хранения 1 день. Релизные и ручные ветки загрузки не выполнялись: интеграция GitHub в этой сессии не предоставляет запуск `workflow_dispatch`.

Этот PR содержит сами workflow, поэтому его сравнение с `main` намеренно запускало все платформы. Отдельный docs-only CI run после изменения здесь не измерен; путь Markdown и fail-closed правила проверены 18 unit-тестами классификатора. Ручная упаковка требует проверки после появления этих workflow в `main`.

## Сбережённые и ожидаемые минуты

- **Повтор после merge:** семь исторических повторов на `main` стоили 69,06 runner-минут / 113,88 эквивалентных минут. Новая политика отключает их для защищённой `main`; экономия этого объёма пока прогнозная, так как PR ещё не объединён и post-merge запуск новой политики не измерен.
- **Markdown-only PR:** ранее два таких PR потратили 20,37 runner-минут / 33,92 эквивалентных минут на тяжёлые Desktop jobs. Среднее — 10,19 / 16,96 минут на PR. Новый путь запускает только лёгкие jobs; по длительностям соответствующих jobs в полном запуске его ориентир — около 0,17 runner-минуты. Значит, возможная экономия около 10,02 runner-минут / 16,79 эквивалентных минут на docs-only PR — **прогноз**, пока не проверенный отдельным docs-only PR.
- **Кэширование:** реальные cache hit/miss и восстановление подтверждены. Старые установки Qt Desktop (0,97–2,13 минуты на runner), Qt/aqt Android (около 1,15) и Ninja (0,70–1,35) сравниваются с восстановлением из нового кэша (Qt Desktop — 17–21 секунда, Android Qt — около 13 секунд; Ninja cache восстановился менее чем за несколько секунд). Ожидаемое сокращение при следующих полностью тёплых трёхплатформенных запусках — ориентировочно 4–9 runner-минут / 6–12 эквивалентных минут. Это **оценка по историческому времени установки и текущему времени восстановления**, а не уже сэкономленные минуты.
- **Артефакты:** исторические 90,43 MB на каждый из двух сохранённых Desktop runs могли занять до 16,3 GB-дней за 90 дней. В проверенном новом PR run не было скачиваемых приложений; fixtures занимают 2,51 MB в течение 1 дня.

Измеренная экономия проекта пока равна нулю: PR ещё не объединён, поэтому post-merge политика и отдельный docs-only PR ещё не прошли эксплуатационную проверку. Приведённые выше docs-only, post-merge и cache оценки обозначены как прогнозы.
