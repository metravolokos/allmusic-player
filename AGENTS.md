# Правила работы Codex в репозитории AllMusic Player

Проект: личный Qt 6/C++/QML музыкальный плеер для Windows, Linux, Android; источник Mail WebDAV `/AllMusic`. Владелец проекта **не программист**, поэтому ответы должны быть понятны по-русски.

## Постоянный язык пользовательских материалов

Вся пользовательская документация, названия и описания Pull Request, отчёты Codex, инструкции и пояснения должны быть на русском языке. Программный код, технические идентификаторы и стандартные названия библиотек допускаются на английском.

## Обязательная проверка рабочего checkout перед каждой задачей

**Нулевая стадия, до чтения/изменения кода, установки зависимостей и запуска субагентов.** Не считать выбранное в интерфейсе имя ветки доказательством актуальности файлов.

1. Установить из Issue/задания **репозиторий, исходную ветку и ожидаемый базовый commit SHA**. Проверить в рабочем каталоге `git rev-parse --show-toplevel`, `git rev-parse HEAD`, `git status --short --branch`, `git remote -v`. Если remote содержит учётные данные, скрыть их в отчёте. При отсутствии remote не утверждать, что checkout синхронизирован с GitHub.
2. Подтвердить, что текущий `HEAD` — **указанный базовый SHA или явно допустимый в задании потомок** (например, уже существующая рабочая ветка с разрешёнными коммитами). Проверить ключевые исходные файлы/модули текущего этапа, а не только SHA и название ветки. Указать в первом отчёте фактический HEAD, ожидаемый SHA и результат проверки файлов.
3. Если checkout неправильный/неполный, **не начинать разработку и не запускать субагентов**: сначала попытаться переключить/синхронизировать рабочую копию **штатными безопасными средствами** облачного окружения или `git fetch`, не теряя несохранённые изменения. Не делать `reset --hard`, удаление файлов, обход TLS/прокси или подмену источника без согласования.
4. Если GitHub недоступен из shell (proxy/network/auth) и верный checkout нельзя подготовить, **остановиться**. Сообщить ожидаемый и фактический SHA, отсутствующие ключевые файлы, краткую обезличенную причину ошибки и следующий конкретный шаг: создать задачу с правильно опубликованным окружением или исправить checkout. **Не воссоздавать с нуля уже существующие компоненты** и не выдавать документальную копию за исходный код.
5. Повторить проверку HEAD/ключевых файлов после восстановления checkout и перед созданием PR; CI и APK запускать только на подтверждённой целевой ревизии. При изменении базовой ветки пересогласовать допустимую ревизию, а не молча переходить на иной код.

Эта проверка относится ко **всем** следующим задачам, включая Android, Desktop, исправления и исследования.

## Перед каждой задачей

1. Прочитать `README.md`, `SPEC.md`, `ARCHITECTURE.md`, `ROADMAP.md`, `DECISIONS.md`, `STATUS.md` и требования конкретной задачи.
2. Разделять утверждённые требования, предложения и непроверенные гипотезы. Не приписывать тестам или пользователю несуществующие подтверждения.
3. Для значимого изменения предложить краткий план, список файлов, тестов, рисков и решений, требующих утверждения. Если задача требует архитектурного решения или изменения удалённых данных — запросить явное согласование.
4. Не переходить на следующий этап дорожной карты без явного разрешения владельца.

## Во время работы

- Предпочитать небольшой проверяемый срез, не переписывать несвязанные модули.
- Соблюдать границы модулей, не блокировать UI сетью/базой/декодированием.
- В первую версию не добавлять удалённые операции записи/удаления. Не делать скрытых или тестовых запросов записи к живому облаку.
- **Никогда** не просить владельца вставить пароль, токен или содержимое личной медиатеки в чат/issue/PR. Не хранить секреты в Git, документах, скриншотах, логах. Разрешать реальные интеграционные тесты только отдельно и безопасно.
- Для тестов использовать фиктивные аудиоданные с законным происхождением и локальный mock WebDAV. Не скачивать для CI реальные музыкальные файлы пользователя.
- Не утверждать работоспособность MP3/FLAC/AAC/ALAC на всех системах без целевых испытаний.
- Новые зависимости выбирать с проверкой лицензий, платформенной поддержки, обновлений и security impact.
- Если отсутствует SDK/доступ или тест не запускался, отметить как `НЕ ПРОВЕРЕНО`, а не `ПРОЙДЕНО`.
- Сложные задачи декомпозировать, но не расширять объём текущей задачи без согласования.
- **CI прежде всего проверяет код.** В Draft PR выполняются быстрые проверки без публикации сборок. В Ready PR при необходимости Android-сборки после успешного аудита APK автоматически сохраняется комплект APK и лицензий как скачиваемый артефакт для ручной приёмки владельцем; повторно нажимать Run workflow не нужно. Windows ZIP и WebDAV test kit по-прежнему сохраняются только по явному ручному запросу или при релизе. После merge в main тяжёлые платформенные сборки не повторяются. Никаких секретов и личных данных в артефактах. Сборка и скачивание APK не означают успешной ручной приёмки.

## По завершении

Выдать отчёт на русском языке:
1. Что изменено простыми словами.
2. Список затронутых областей/файлов.
3. Реально исполненные тесты: команды, платформа, результат.
4. Неисполненные тесты и причина.
5. Как пользователю воспроизвести проверку шаг за шагом.
6. Ошибки/риски/технический долг.
7. Изменения в `STATUS.md` и, если нужно, в `DECISIONS.md`.
8. Ссылку на PR и рекомендацию: принимать / не принимать с объяснением.

Никогда не писать «всё работает», если проверены только сборка или unit-тесты. Коммит/PR не означает приёмку этапа. Ответы краткие, но достаточные; при выборе технологий указывать рекомендуемый вариант и альтернативы.
## Единая политика приёмки Windows Desktop — решение владельца 29.10.2026

- Для задач и отчётов используем категорию **Windows Desktop (11/10)**. Приоритетная физическая система ручных тестов — **Windows 11**; её успешная проверка удовлетворяет Windows-части обычной приёмки этапа.
- Windows 10 остаётся целевой системой совместимости, но её отдельное ручное испытание **не обязательно для приёмки каждой задачи** и не блокирует следующий этап, если владелец явно не назначил проверку Windows 10 или если обнаружен Windows-10-специфичный риск.
- **Никогда не приписывать Windows 10 результат, полученный только на Windows 11**, и наоборот. В доказательствах указывать точную ОС, успешные Windows Server CI отдельно от тестов на физическом ПК.
- Не запрашивать повторную проверку одного и того же сценария на Windows 10 без причины. Общие обязанности по сборке Windows x64, Linux и Android сохраняются в рамках соответствующих задач.

Она имеет приоритет над более ранними формулировками о ручном утверждении каждой задачи или GitHub merge **только** в пределах строго определённой низкорисковой работы. Нельзя трактовать это как освобождение от проверки checkout, CI, безопасности, аппаратной приёмки, релиза и архитектурных решений. Доступность инструмента запуска Codex Cloud по расписанию не доказана: нельзя приписывать планировщику возможности Cloud execution.
