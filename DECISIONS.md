## Исследование 001-B1 — 29.10.2026

Источник: прямое разрешение владельца на локальный прототип после PR #4/#6.
Ограниченный адаптер QMediaPlayer/Qt Multimedia с FFmpeg реализуется как кандидат,
без окончательного IPlaybackEngine или сетевого источника. D-008 и D-009

ffprobe реально подтвердил MP3, FLAC 16 bit, AAC LC ADTS/M4A и ALAC 24 bit M4A

Результаты и ограничения: [отчёт](docs/001-B1-REPORT.md).
Частичная загрузка/Range, gapless, Android audio, окончательный выбор движка
и способ распространения публичного релиза остаются открытыми.

Результаты 001-B1: Qt 6.12.0 / FFmpeg 9.0.1 действительно декодировали пять
образцов в ненулевой PCM на Linux CI; Windows PCM и упаковка подтверждены
Desktop run 40928437106 для финальной реализации df1846a. Перенос CMake-цели
подтверждён успешным APK-аудитом run 40928437092. Проблема общего SOURCE_DIR Qt сканера устранена разделением CMake scope,
без ослабления аудита APK. Это результат эксперимента, не утверждение движка.
Слышимый звук, прочие профили, сетевые источники и Android audio НЕ ПРОВЕРЕНЫ.

001-E проверяет синтетические аудиофайлы только через локальный loopback mock.

повтора того же 429 Range последний прогон зелёный. Это была межтестовая изоляция mock,

конца. HTTP 200/206/416,
ETag, неполный ответ, искусственная задержка/скорость, 429 с Retry-After,

ответа 2 500 мс, повторный запуск того же сетевого трека и сохранение источника
при Stop локального файла. Пауза, продолжение, смена трека и уничтожение

покрытые сценарии, но не доказывает отсутствие всех возможных гонок.

## Ограниченное решение для 002-C — 30.10.2026

По прямому объёму Issue #22 Desktop получает потоковый источник `QIODevice`
на базе `QMediaPlayer`; Cloud Mail Range выполняется отдельным worker-потоком,
а существующее loopback устройство не меняется. Это позволяет использовать
ранее проверенный декодер и lifecycle-управление только для MP3/FLAC, сохраняя
ограничение памяти страниц и строгую проверку каждого ответа. Архитектурного
выбора, требующего отдельного решения владельца, не возникло.

Это не закрывает D-027–D-029 и не выбирает финальный playback/provider API.
При сильном ETag используется `If-Range`. Если сервер не даёт сильный ETag,
размер и отдельные Range-поля позволяют обнаружить часть изменений, но не
доказывают, что байты из разных запросов принадлежат одной неизменной версии.
В таком случае приложение не выдаёт размер за гарантию целостности.
Реальные запросы и звук остаются проверкой владельца на Windows 11; CI работает
только с синтетическими файлами и локальным mock.

Владелец выбрал изолированный вариант из Issue #24. Android APK принудительно
запрашивает Qt FFmpeg backend, включает только его multimedia plugin и исключает
Android system media plugin; FFmpeg protocol whitelist ограничен `file`.
Синтетические MP3/FLAC открываются из seekable
`QBuffer`; короткий WAV-тест 002-A сохранён как отдельный режим этой сборки.
Package ID 002-D отличается от 002-A. CI проверяет runtime-библиотеки, итоговый
manifest, notices и размер APK.

Это ограничение задачи, не решение о production playback. Cloud Mail, чтение
пользовательских файлов, сеть, полноценный телефонный плеер, background service,
MediaSession и постоянный кэш не входят. Сборка и package audit не доказывают
слышимый звук на Huawei; ручная проверка остаётся отдельной. D-008/D-009 и выбор
основного `IPlaybackEngine` сохраняют прежний статус. Если эксперимент выявит
существенную стоимость, разрешения или лицензионное ограничение, зафиксировать
результаты и варианты до расширения реализации.


## Диагностическое уточнение 002-D — 31.10.2026

Ручной тест на Huawei подтвердил бесшумный WAV при загруженном Qt FFmpeg,
найденном default audio output и движущейся позиции. Выбор MP3/FLAC не сработал,
поэтому их аудио путь пока не испытан. Причину тишины нельзя вывести из этих
наблюдений.

Для следующей сборки оставляем существующий QMediaPlayer + Qt FFmpeg путь без
смены движка и добавляем только наблюдаемость: активная дорожка/hasAudio,
состояние ошибки, текущий QAudioOutput device/volume/mute и агрегированные
счётчики QAudioBufferOutput. Короткий синтетический PCM сигнал через QAudioSink
на том же устройстве проверяет Android audio path отдельно. Qt 6.12 Android
реализует QAudioSink через AAudio; исходник также проверяет открытие stream и
  предупреждает, если параметры потока не совпали с запросом. В Qt FFmpeg
  AudioRenderer отправляет данные в sink и отдаёт декодированные кадры
  QAudioBufferOutput. Эти места задают проверяемые гипотезы, не доказывают
  неисправность конкретного устройства. Если direct sink слышен при молчащем player,
следует исследовать декодер/связку QMediaPlayer и output. Если оба теста молчат,
сначала проверить устройство, системную громкость и маршрут. Это диагностические
развилки, а не установленные причины. PCM не сохраняется.

Архитектурный выбор о production engine не возникает. Не добавлять Android
permissions, не подключать Cloud Mail и не принимать этап до слышимого сигнала
на физическом Huawei.
